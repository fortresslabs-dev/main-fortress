Pipeline 1 & Pipeline 2 Database Design

One PostgreSQL (Aurora pgvector) schema, two pipelines. Pipeline 1 (Fortress Cloud) scrapes and publishes regulatory rules; Pipeline 2 (bank-side) consumes them and runs the compliance program. This document inventories every table, shows BSA/AML-grounded sample rows, and maps the relationships — including the joins that cross the pipeline boundary.

The two-pipeline model

There is a single ORM model file and a single Alembic migration chain, so alembic upgrade head materialises the same schema on either database. The pipelines differ by what they write, not by which tables exist. The split below is by ownership — which process is the author of record for each table.

Pipeline 1 — Fortress Cloud

PIPELINE_MODE=pipeline1 · EventBridge → ECS scraper

Scrapes 17 federal + 5 state regulatory connectors, embeds rules with Bedrock Titan, and publishes a versioned rule corpus the banks pull from. Author of the public regulatory dataset.

  • Writes rules, OFAC SDN data, obligations, enforcement & deadlines
  • Owns the monotonic sync_version every bank replicates against
  • Never sees customer/transaction data

Pipeline 2 — Bank-side

PIPELINE_MODE=pipeline2 · per-bank Docker / ECS

Pulls the P1 corpus, screens live transactions, runs the 6-agent test factory off JIRA, and drives the CCO exam-readiness dashboard. Author of everything bank-specific.

  • Validators & OFAC screening with full case management
  • Controls, tests, findings, governance evidence, signed exports
  • Holds PII; isolated per bank
The bridge: P2 replicates P1's compliance_rules + obligations locally via the sync API (keyed on sync_version). Most P1→P2 links are therefore logical joins on business keys (rule_id, obligation_id) rather than enforced foreign keys — the one hard FK that crosses the line is control_obligation_mappings.obligation_id → obligations.obligation_id.
