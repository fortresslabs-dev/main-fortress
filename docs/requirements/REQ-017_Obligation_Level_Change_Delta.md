# REQ-017: Obligation-Level Change Delta Detection

## Overview
**Priority:** Medium
**Type:** Enhancement — Pipeline 1 and Pipeline 2
**Source:** Competitor gap — Compliance.ai / Corlytics
**Pipeline Impact:** Pipeline 1 (enhanced diff) + Pipeline 2 (diff consumption)
**Status:** Backlog

## Business Context
When a compliance rule's SHA-256 hash changes, the current system detects the change and
syncs the updated record — but it cannot identify which specific obligations within that
regulation changed. A hash change on the entire BSA/AML handbook could mean one sentence
was clarified or the entire section was rewritten. Without obligation-level diffing, the
system could sync a significant rule change, yet the Generation agent produces the same
test scenarios as before because the `rule_type` taxonomy didn't change even though the
underlying obligation did. Compliance.ai diffs at the obligation level. This enhancement
brings that capability to the existing sync infrastructure.

## Requirements

### Functional Requirements
1. Enhance `ComplianceRule` model in `src/models/database.py`:
   - Add `previous_content` text field (stores prior version of rule content)
   - Add `change_delta` JSON field: stores obligation-level diff from last version
   - Add `changed_obligations` JSON array: list of obligation IDs (from REQ-010) that changed
   - Add `change_type` enum: `added` / `modified` / `removed` / `clarified`
2. Add `ObligationDiffService` in `src/services/obligation_diff_service.py`:
   - Input: previous rule content + new rule content
   - Process 1: structural diff — Myers diff algorithm on paragraph/sentence boundaries
   - Process 2: LLM semantic diff — "Describe what obligation changed between these two
     versions, if any. State the old obligation and the new obligation."
   - Output: `ObligationDiff` object with `changed_sections`, `added_obligations`,
     `removed_obligations`, `modified_obligations`, `semantic_summary`
3. Enhance `ScraperScheduler._run_scrape_cycle()` in Pipeline 1:
   - Before upserting a rule with a changed hash, run `ObligationDiffService`
   - Store `change_delta` and `change_type` in the updated `ComplianceRule` record
   - Populate `changed_obligations` with obligation IDs from `obligations` table (REQ-010)
4. Enhance sync payload: include `change_delta` and `changed_obligations` in the
   incremental diff sent to Pipeline 2
5. Enhance `UpdateService` in Pipeline 2:
   - When consuming a changed rule, update local `obligations` table for affected obligation IDs
   - Trigger `ObligationCoverageScorer` (REQ-010) re-run for affected regulation

### Pipeline 1 Changes
- Add `previous_content`, `change_delta`, `changed_obligations`, `change_type` columns
  to `compliance_rules` table via Alembic migration
- `ObligationDiffService` runs in `ScraperScheduler._run_scrape_cycle()` after hash change
  detected, before DB upsert
- Include diff data in sync payload

### Pipeline 2 Changes
- `UpdateService` processes `change_delta` from sync payload
- Trigger `ObligationCoverageScorer` re-run when obligations change
- `RegulatoryChangeRecord` (REQ-013) auto-populated with `semantic_summary` from diff

## Acceptance Criteria
- [ ] `ObligationDiffService` correctly identifies added/removed sentences between two
      versions of a rule text (unit test with synthetic before/after content)
- [ ] `change_type` field correctly set for added, modified, and removed rules
- [ ] `changed_obligations` array populated with correct obligation IDs when REQ-010 is implemented
- [ ] `semantic_summary` generated by LLM is a non-empty plain-English description of the change
- [ ] Pipeline 2 `UpdateService` processes `change_delta` without error for empty delta (no change)
- [ ] Alembic migration runs cleanly on existing DB

## Technical Notes
- Structural diff: use Python `difflib.unified_diff` at the sentence level
  (split on `. ` boundaries) as the first pass — cheap and fast
- LLM semantic diff: only call LLM when structural diff finds actual changes
  (non-empty diff output) — this avoids LLM cost on unchanged rules
- `change_type: "clarified"` applies when the structural diff is minor (< 20% of content
  changed) but the semantic meaning is the same — LLM should detect this and set the type
- `previous_content` storage: only store the most recent previous version (not full history);
  full history is tracked in `regulatory_change_records` table (REQ-013)
